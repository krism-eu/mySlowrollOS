# atomic-update 5.7.1 — design contract

**Status:** sole supported implementation candidate; not production-stable.
**Validation:** source-level review and CI checks are not substitutes for an
end-to-end VM crash/recovery matrix. Availability of a source or RPM does not
mean that this matrix has passed.

## Single-version policy

The 5.7.1 implementation is the only maintained update engine. The older source
and its compatibility branches have been removed intentionally. This is a
**clean state break**: never upgrade this package while another updater has a
transaction pending. There is no migration or reading of older state formats.

Release version: `5.7.1`.
State schema: `1`, independent of release version.
Stable paths:
- `/var/lib/myslowroll/atomic-update/{state,history.log}`
- `/var/cache/myslowroll-atomic-update/`
- `/var/log/myslowroll-atomic-update/`
- `/run/myslowroll-atomic-update.lock`

TARGET ownership description: `mySlowrollOS atomic-update TXID`.
ZYpp userdata: `myslowroll-atomic-update:TXID`.
The state and cache namespaces must not change for routine release bumps.

## Non-negotiable invariants

- Supported host: openSUSE Slowroll, classic RW Btrfs root with Snapper root,
  systemd-boot and sdbootutil. RPMDB is inside the root snapshot.
- /var, persistent state, logs, cache and workstation /home are outside the
  root snapshot.
- No timer, daemon, background automatic upgrade or unattended scheduler.
- SOURCE remains the running RW snapshot, never the RPM transaction root.
- Zypper modifies packages exclusively inside an offline tukit TARGET.
- TARGET becomes default only after plan, manifest, critical-package,
  OS identity and bootability checks.
- Effects outside Btrfs root snapshots (including boot storage) must be handled
  explicitly; rollback is not an all-filesystem restore.
- Unknown results fail closed; no blind abort of active/default TARGETs.
- Confirmation is after reboot. Explicit rollback needs separate confirmation.
- `prune` only removes cache/log artifacts; never Btrfs snapshots.

## Transaction lifecycle

Native states:

- `planning`, `planned`, `revalidated`, `opening`, `target`
- `verified`, `committing`, `pending-reboot`, `needs-inspection`
- `rollback-pending`, `confirmed`, `aborted`, `rolled-back`

Only hashes needed for verification and recovery are persisted:
`plan_hash`, `source_fingerprint`, `rpmdb_post_hash`.
The source fingerprint combines the installed RPM manifest and semantic ZYpp
repository/solver policy. The boot ID and SOURCE/TARGET identity are separate
structural guards. Avoid whole-/etc and CLI-help/version hashing.

`plan` refreshes repositories, downloads candidate RPMs and computes one
canonical PREPARED XML solver plan, exact operations and expected RPM manifest.

After explicit user confirmation, `upgrade` REVALIDATES by rechecking the
SOURCE, refreshing metadata, re-running the solver, comparing canonical hashes
and exact operations and completing the RPM cache. Repository drift invalidates
the transaction **before** tukit opens a TARGET.

Persist `revalidated` before calling `tukit open`. Failures after opening
must not be treated as safe to retry without evidence.

Perform the RPM transaction inside TARGET, collect the actual RPM manifest,
compare it to the expected manifest, validate critical packages and OS ID,
check both SOURCE and TARGET bootability, then sync and close TARGET.

Accept Zypper exit 102/103 only as permission to run the full verification;
exit 107 and other unexpected nonzero codes fail closed.

## Recovery contract

`recover` is the safe classifier; `recover inspect` is read-only.
Typed actions are `recover abort-target N`, `recover adopt-target N` and
`recover clear-opening`.

`rollback [SOURCE]`, with its existing typed confirmation, also resolves
`needs-inspection` for `boot-mismatch` and `target-active-or-default`. It only
accepts the recorded SOURCE and requires active/default to belong to the
recorded SOURCE/TARGET pair. Other inspection kinds remain blocked.

This recovery path keeps the failed update TXID and snapshot identities until
Snapper stages a new rollback snapshot. It does **not** persist `aborted` first:
that would create an interruption window with the failed TARGET still default
and the recovery context lost. The intermediate inspection kind is
`rollback-recovery`, using the existing state schema and fields. The new
snapshot carries the exact description
`mySlowrollOS atomic-update rollback TXID source=N`; recovery checks this before
adopting a changed default. An interruption before staging restores the typed
rollback route, requiring confirmation again. No failed TARGET is deleted by
this path.

- Snapper listing errors must never be mistaken for zero owned TARGETs.
- An unrecorded TARGET may be aborted only if exact TXID ownership is uniquely
  established, the snapshot is inactive/non-default and is quiescent.
- A TARGET that is active or default must never be blindly aborted.
- Adoption requires positive evidence of a previously verified TARGET,
  its current RPM manifest and critical-package/boot invariants.
- Incomplete or ambiguous close/abort outcomes require classification using
  observed state rather than simply trusting the command return code.
- After TARGET removal is proven, boot-entry cleanup is best-effort.
- Never clear an opening record if the Snapper enumeration fails or an owned
  TARGET may exist.

Do not remove or automatically rewrite a user's /home files. No background
backup, snapshot cleanup, or installation jobs are introduced by this updater.

## Explicit gate before release

1. Static syntax and design checks plus focused mocked regressions.
2. Review capability gates, SOURCE/TARGET safety and typed recovery paths.
3. Fresh installation in a VM using the intended Slowroll layout.
4. Validate no-op, successful offline update, repository drift, and rejected
   critical-package changes.
5. Inject process termination during opening, TARGET updating, close and abort.
6. Verify unambiguous/no-target and ambiguous recovery cases separately.
7. Validate boot, post-reboot confirm, explicit rollback and boot-entry cleanup.
8. Only after these pass: promote to main and publish the RPM on OBS.

The implementation is **not yet designated production-stable**.

## Review checks (2026-10-08)

`tests/recovery-review.sh` adds 16 isolated mocked regressions covering failed
boot recovery, active TARGET rollback, cancellation, unrelated states/defaults,
interruption before and after staging, shared filesystem UUID accounting,
zero/nonzero RPM epochs, one batched critical-package query, tukit description
capability, XML hashing failure, visible abort reasons and Snapper diagnostics.
The existing `tests/ci-regression.sh` remains in the CI job.

RPM manifests normalize explicit epoch zero identically on SOURCE and TARGET;
nonzero epochs remain significant. `VERIFY_PAYLOADS` was removed: an unfiltered
`rpm -V` is not a suitable integrity gate for intentionally modified configs.
The critical-package presence check remains, using one RPM query.

Still to verify on the actual Slowroll VM (not covered by mocked passes):

- Count explicit zero epochs with `rpm -qa --qf '%{EPOCH}\n' | grep -c '^0$'`
  (`grep` returns 1 when the count is zero), and compare real RPM/XML editions.
- Check `tukit --help` and the verbatim TXID description in Snapper after open.
- Check the verbatim rollback description and actual systemd-boot entries.
- Perform update, failed TARGET boot, manual SOURCE boot, `recover`, explicitly
  confirmed `rollback`, reboot and rollback confirmation.
- Inject interruption/power loss around Snapper rollback and confirm recovery
  with both the same boot and a changed boot ID. Same-boot mocked interruption
  tests do not establish power-loss recovery across boot IDs.

Do not replace the updater during a pending transaction. In particular,
normalization changes must not be introduced midway through a saved RPM plan.
