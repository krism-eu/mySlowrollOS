# atomic-update 5.7 — design contract

Baseline: atomic-update 5.6.1-guarded. This is an evolution, not a rewrite.

## Non-negotiable invariants

- Host: openSUSE Slowroll, classic read-write Btrfs root, Snapper root, systemd-boot/sdbootutil.
- No timer, daemon, unattended update or automatic scheduler.
- SOURCE remains the running RW snapshot and is never the RPM transaction root.
- All package changes happen only in an offline TARGET created by tukit.
- TARGET becomes default only after the solver result, RPM manifest, critical packages, OS identity and bootability checks pass.
- /var and boot storage are external side-effect domains and are treated explicitly.
- If TARGET is active or default, recovery never deletes or aborts it blindly.
- Ambiguous situations fail closed.
- confirm remains post-reboot and keeps the 5.6.1 narrow allowance for purge-kernels only.
- rollback remains explicit and separately confirmed.

## 5.7.1 implementation strategy

5.7.1 is deliberately an incremental hardening of the known 5.6.1 engine, not
the clean rewrite originally sketched for 5.7.  This reduces regression risk and
keeps in-flight 5.6.1 transactions recoverable.

The implementation therefore retains the proven 5.6.1 state/cache namespace and
most of its persisted fields, including the RPM/ZYpp/cache/source/toolchain hash
slots.  State version 6 can read version-5 state.  A 5.6.1 pending-reboot
transaction remains confirmable after the atomic-update RPM itself is upgraded.

Native 5.7.1 adds two important durable states:

- revalidated: PREPARED has passed the final current-metadata solver comparison
  and no TARGET has yet been opened;
- needs-inspection: an open/close/abort/rollback outcome is ambiguous enough
  that automatic mutation is forbidden.

The 5.6.1 intermediate states remain accepted because they are still useful for
compatibility and conservative recovery.  The long-term cleanup to a smaller
state machine is deferred until after 5.7.1 has passed the VM matrix.

The toolchain field remains a 64-hex value for state compatibility, but in 5.7.1
it hashes a stable semantic capability token rather than complete --help/version
text.  ZYpp/cache/source component hashes are also intentionally retained in
this hybrid release.

## PREPARED -> REVALIDATED solver contract

Planning produces one canonical PREPARED solver result after refresh and
pre-download. It records the canonical plan hash, exact operations and expected
RPM manifest.

Immediately before tukit open, upgrade performs REVALIDATED:

1. check the required tukit/sdbootutil capabilities;
2. verify the prepared RPMDB, ZYpp configuration and package-cache hashes;
3. refresh repository metadata;
4. verify SOURCE/RPMDB and ZYpp configuration did not change as a side effect;
5. rerun the solver with the refreshed metadata;
6. compare canonical plan hash and exact operations with PREPARED.

If repository publication changes the solver result, the prepared transaction is
invalidated before any TARGET is opened; the user must create a fresh plan and
download its packages.  If the result is unchanged, the already verified cache
is reused.

Only after this succeeds is status=revalidated persisted.  tukit open refuses
to run unless that durable barrier exists.

## Capability checks

Do not hash complete --help output. Test the capabilities actually used:

- tukit: open, call, close, abort;
- sdbootutil: add-all-kernels, is-bootable, remove-all-kernels, cleanup;
- --disable-predictions where required by cleanup operations;
- required commands and the XML parser self-test.

A harmless help-text/version change must not invalidate a valid prepared plan.
A missing required capability must still fail closed.

## SOURCE consistency

The clean single source_fingerprint design is deferred.  5.7.1 preserves the
5.6.1 split SOURCE barriers to minimize risk:

- prepared RPMDB manifest/hash;
- post-open SOURCE RPM hash;
- post-open /etc semantic tree hash with the existing narrow volatile exclusions;
- active/default snapshot identity and boot_id.

These checks are repeated across the destructive boundaries so SOURCE drift
still blocks commit.  Consolidating them into one fingerprint is a later
maintenance cleanup, not a 5.7.1 requirement.

## TARGET quiescence

Before any automatic boot-entry cleanup or tukit abort, TARGET must be proven
quiescent.

The check must refuse cleanup if the transaction can still be running or if
quiescence cannot be demonstrated. At minimum it checks that no live ZYpp/RPM
work for the transaction is observable and that TARGET is neither active nor default.

If quiescence cannot be proven, transition to needs-inspection. Never issue a
second blind abort.

## Typed recovery

recover remains the safe default classifier.

needs-inspection exposes explicit typed recovery actions instead of guessing:

- inspect: read-only diagnosis of state, SOURCE/TARGET, boot state and logs;
- abort-target: permitted for a quiescent, non-active, non-default TARGET that
  is either recorded in state or uniquely owned by this TXID via the exact
  tukit/Snapper description;
- adopt-target: permitted only when TARGET is already the verified/default result and all invariants pass;
- clear-opening: permitted only when no TARGET matching the transaction can be found by state or exact description ownership and SOURCE/default are unchanged.

No recovery action deletes an active/default snapshot.

## Preserved 5.6.1 behaviour

Keep:

- parser self-test;
- canonical plan hash and exact operation list;
- expected RPM manifest;
- critical-package removal protection, including atomic-update itself;
- zypper 102/103 acceptance only as permission to run the full TARGET verification;
- zypper 107 and other non-zero failures fail closed;
- target TTL;
- SOURCE/TARGET bootability checks and sdbootutil repair;
- sync barriers before close;
- explicit reboot behaviour;
- confirm and narrow purge-kernels tolerance;
- rollback/recover/prune commands;
- state/cache/log outside the root snapshot and RPMDB inside it;
- /home outside the root snapshot on the intended workstation;
- no Snapper ZYpp nested snapshot inside TARGET.

## Packaging

5.7 stays a separate atomic-update RPM installed by the workstation profile but
not anchored by criscore1/criscore2. The spec must retain explicit runtime
requirements, including diffutils for cmp.

Do not publish to OBS or merge to main until:

1. bash -n and source-level audit pass;
2. 5.6.1 -> 5.7 state compatibility is explicitly decided/tested;
3. VM matrix covers successful update, no-op, solver drift, kill during TARGET
   update, ambiguous open/close, TARGET cleanup, reboot/confirm, recovery and rollback.


## Description namespace

New 5.7.1 transactions use the description prefix `mySlowrollOS v6` so TARGET
ownership can be recovered when tukit stdout parsing is ambiguous.  Legacy
5.6.1 transactions used `mySlowrollOS v5`; their pending-reboot compatibility
comes from the retained v5 state/cache namespace, not from v6 description lookup.
