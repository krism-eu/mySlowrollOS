# Architecture decision — 2026-10-08

## Installation and sources

Stock Agama 24, product Slowroll, remains the interactive installer.
The active entry point is `agama/profile-final.jsonnet`.
Storage and authentication are omitted: disks, partitions, formatting, username
and credentials are chosen in the UI. No unattended hardware installation.

Package selection uses three deliberately separate source lists:
- Protected core: `criscore1/2` direct requirements in
  `obs/criscore1/criscore1.spec`. These must also appear in the persistent layer.
- Workstation manifest: `Requires` in
  `myslowroll-workstation/myslowroll-workstation.spec`, expanded into individual
  installation requests. The corresponding metapackage RPM is currently NOT
  published on OBS or installed by Agama; these extras are not yet retained
  as hard requirements during subsequent upgrades.
- Agama install-only: `agama/install-only-packages.txt`; these packages are
  requested at installation but are NOT `Requires` of the workstation or the
  protected core. All YaST modules including `yast2-snapper` live here so they
  cannot block a future dup through our RPM anchors.

`agama/profile-policy.json` defines the profile structure.
`agama/generate-profiles.py` merges the persistent and install-only lists
without duplicate packages and generates the final profile, an identical VM
test profile, and a software-only diagnostic subset. It rejects overlap,
core drift between anchors and protected requirements missing from the
persistent workstation manifest. This does not require OBS at generation time.

The protected core now has one reproducible source:
`core/protected.seed` + `obs/criscore1/criscore1.spec.in`, generated by
`core/generate-criscore-spec.py` and checked during profile generation.
Agama does not request the unpublished `myslowroll-workstation` RPM. It
requests the individual 158 workstation packages and 10 YaST install-only
packages. `criscore1/2` still protect the approved 108-package core.
The installer presets Italian locale/keymap without overriding storage,
accounts or timezone.

OBS may still contain older packages: GitHub commits do not rebuild OBS.
Before the VM install, check that the published criscore1/2 RPMs match the
generated spec and that atomic-update 5.7.1 is available in OBS. The
workstation metapackage is optional for this installation and may be published
later; doing so would not require repeating the OS installation. The current
atomic-update 5.7.1 source is merged into main and is available as an OBS RPM,
but its recovery scenarios still require VM validation.

## Trust and policy

OBS repository:
`https://download.opensuse.org/repositories/home:/krism/openSUSE_Slowroll/`

Trusted fingerprint: `85283DD3E1AFA9EA668E20653505E29C78A00759`.

All deployed policy files and scripts use full commit-SHA URLs recorded in
`agama/assets-revision`, including the OBS public key. Keep signature checking
enabled. The final repo file requires gpgcheck=1, repo_gpgcheck=1 and its local key.

Agama v24 adds the first user to wheel. The local sudo and polkit policy grants
passwordless administration to wheel (polkit additionally requires a local active
session). No active custom script creates users, clears passwords or changes PAM.
Agama's group assignment is best effort, so verify it after installation.

Zram is configured explicitly using zram-generator:
min(RAM / 2, 4096 MiB), zstd, swap priority 100.
On the target 16 GiB machine this gives a 4 GiB logical swap device.
Disk swap remains a manual storage choice; the intended layout uses none.

The post-chroot script selects native SDDM and graphical.target before reboot.
The init script imports the OBS key and applies runtime service policy.
The RPM policy spec deliberately contains no %post service actions, so later
updates cannot re-enable disabled services or reset SDDM aliases. The preset
records initial defaults; the Agama one-time scripts handle bootstrapping.
A full first-boot VM check must validate the resulting service state.

## Validation boundaries

Earlier Agama 24 Build11.3 results established repository trust, package
resolution and readiness of the software proposal. They do not establish
successful installation or boot of this revised final profile.

Static checks can establish generated-file consistency and shell syntax only.
Agama v24 writes profile files before storage finalization installs the bootloader.
The supplied /etc/kernel/cmdline still needs an installed-system check: this
revision does not assert whether the bootloader preserves or regenerates all
root/AppArmor parameters.

Before hardware installation, complete one VM installation using the actual
final profile and perform the checks in agama/tests/TEST-02.md.
